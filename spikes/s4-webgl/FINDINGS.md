# S4 结论：桌面层能拿到硬件加速，但遮挡必须自己检测

在挂到桌面层（`SetParent` 到 WorkerW/Progman 之下）的窗口里跑全屏五层 fbm 噪声着色器，实测：

| 检查项 | 结果 |
|---|---|
| `webgl2` 上下文 | ✓ |
| `WEBGL_debug_renderer_info` 报真实 GPU（非 SwiftShader） | ✓ |
| 全屏着色器帧率 | ✓ 正常 |
| **被最大化窗口完全遮挡时自动停帧** | **✗ 仍然满速** |

**结论：ADR 0016 的地基假设成立。** 桌面层窗口是正常的硬件加速上下文，没有掉进软件渲染。

## 但浏览器不会帮我们省电

被其他窗口完全盖住时，`requestAnimationFrame` 照样以满帧率触发。原因是结构性的：docked 窗口从未被最小化，在 Windows 眼里一直"可见"，所以 `document.visibilityState` 始终是 `visible`，Chromium 的节流逻辑不会介入。

ADR 0016 定的硬线是「被遮挡时 GPU 占用 0%」，因此**遮挡检测必须由我们实现**。

## 采用的判据

Windows 没有便宜的"我被遮挡了吗"API。实现落在 `desktop::occluded()`，只看**前台窗口**：

- 前台窗口是 `Progman` / `WorkerW` / `Shell_TrayWnd` → 用户正在看桌面，即在看我们
- 前台窗口已最小化 → 没挡住
- 否则取它的矩形，覆盖整个主屏才算遮挡

代价是三次 Win32 调用，不需要枚举所有窗口。选前台窗口而非全量枚举，是因为真正会挡住我们的场景就是"前面有个最大化的应用"。**部分覆盖时继续渲染**——那时确实还有一部分画面看得见，这是正确答案而非妥协。

### 一个踩过的坑：比的是工作区，不是屏幕

第一版拿 `GetSystemMetrics(SM_CXSCREEN/SM_CYSCREEN)` 当参照，判定永远不成立。原因是**最大化的窗口只覆盖工作区，不覆盖任务栏那一条**，所以"盖满整个屏幕"这个条件它永远达不到。

改用 `SystemParametersInfoW(SPI_GETWORKAREA)`，并留 8px 余量——Windows 会给最大化窗口留一圈不可见的调整边框，DPI 缩放也有取整误差。

改对之后一次通过。这个判据看起来"更宽松所以更可疑"，实际上是唯一正确的那个，别改回去。

### `visibilityState` 和 `hasFocus` 都不能用作判据

实测桌面层窗口的 `document.visibilityState` 恒为 `visible`，`document.hasFocus()` 恒为 `false`（它平时没有键盘焦点，点击时才争取）。这两个值"都不对"本身就是结论——**浏览器没有任何一个信号能告诉我们有没有人在看**，所以判断必须落在 Win32 那侧。

前端每秒轮询一次。一秒的粒度足够：多画一秒的帧，成本远低于持续查询 shell。

## 遗留

- **多显示器未验证。** `GetSystemMetrics(SM_CXSCREEN)` 只报主屏尺寸，副屏上的窗口和跨屏布局都没测过
- **全屏应用（独占全屏的游戏）未测。** 用户只试了最大化窗口
- 判据看的是前台窗口，所以"两个各占半屏的窗口拼起来把桌面盖满"会被判成没遮挡，仍然渲染。属于可接受的误判方向——宁可多画，不可少画
