# S3 结论：桌面层托管可行，键盘需要显式争取

在一台 Windows 11 上，把记事本 `SetParent` 到桌面层之后实测：

| 检查项 | 结果 |
|---|---|
| 渲染在壁纸之上 | ✓ |
| 其他应用正常盖在它上面 | ✓ |
| 鼠标点击有反应 | ✓ |
| 键盘输入（直接打字） | ✗ |
| 键盘输入（强制争取焦点后） | ✓ |
| 按 Win+D 显示桌面后仍在 | ✓ |
| 最小化所有窗口后可见 | ✓ |

**结论：桌面层能做成完整可交互，但键盘必须显式争取。**

## 为什么鼠标通而键盘不通

结构性原因，不是配置问题。鼠标消息靠命中测试投递，不需要窗口被激活；键盘消息只发给**当前活动顶层窗口**的焦点窗口。`SetParent` 之后我们成了 Progman 的子窗口，活动顶层窗口是桌面本身，键盘于是进了桌面的图标列表。

争取焦点的做法是把本线程的输入队列与前台线程连起来（`AttachThreadInput`），对顶层父窗口 `SetForegroundWindow`，再对子窗口 `SetFocus`，然后断开。这是 Lively 的输入转发所依赖的同一套手法。

Windows 故意让抢焦点变难，所以这招天生脆——但有一条对我们有利的规则：**限制对"刚刚收到用户输入的进程"是放开的**。产品里这段代码只在用户点击我们自己的窗口时执行，那一刻我们正好符合条件。这比 spike 里从终端手动触发的条件更好。

## 这台机器的 shell 布局

发 `0x052C` 之前，`SHELLDLL_DefView`（图标层）挂在 **Progman** 下，11 个顶层 `WorkerW` 全是空的。这是两种常见布局中的 A 型。

经典算法「找到含 DefView 的顶层窗口，取它之后的 WorkerW 兄弟」在这台机器上失效——含 DefView 的窗口是 Progman，而所有 WorkerW 在 z 序上都在它之前。所以选择逻辑改成了「全屏 + 可见 + 自身不含图标层的 WorkerW」，选不到再退回 Progman。

实测挂上去之后，窗口位于**桌面图标之上**。对启动台来说这是想要的效果（我们自己画磁贴，不需要原生图标露出来），但如果将来要做 v2 那种「分区卡片衬在原生图标之下」，得继续找真正位于图标之下的那一层。

## 两个坑

**PowerShell 的 `$null` 传给 `[string]` 参数会变成空字符串**，不是 NULL。`FindWindow("Progman", $null)` 因此变成"找标题为空的 Progman"，永远返回 0。要用 `[NullString]::Value`。这个坑一开始让整份诊断输出都是错的。

**`-Inspect` 必须先发 `0x052C` 再看**。不发消息时看到的是"之前"的布局，据此判断算法会得出错误结论。
