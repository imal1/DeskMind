# 渲染底层：DOM 主导，WebGL 图层 + HTML-in-Canvas 合成

界面的渲染分三层：

1. **DOM 仍然是权威** —— 布局、文字、输入、命中测试、无障碍全部留在 DOM
2. **WebGL 背景层** —— 壁纸之上的生成式光效由着色器绘制，替代现在的 CSS 光晕
3. **HTML-in-Canvas 合成** —— 用 `drawElement` 把选定的 DOM 元素画进 WebGL 纹理，对它们做着色器后期，实现真正的折射玻璃

**背景层先不用库，裸 WebGL2。** S4 的实测推翻了本文档初稿里"直接上 OGL"的建议：全屏着色器连同渲染循环一共一百多行，而 OGL 的价值在场景图与多 pass 抽象，那是折射玻璃阶段才需要的东西。在知道需要哪些抽象之前先买抽象，方向是反的。

**等多 pass 合成写起来费劲了再引 OGL**：零依赖、体积极小、自带 render-to-texture，且 API 刻意做成 three.js 的样子——将来要做真 3D 时换的是库，不是脑子里的模型。三者的迁移路径是连续的，不存在推倒重来。

## 效果的优先级

拷问中把想要的效果拆成四类，取其二先做：

| | 效果 | 状态 |
|---|---|---|
| **B** | 真实折射玻璃：面板扭曲背后的壁纸，边缘有光，看得出厚度 | **先做** |
| **D** | 生成式背景：缓慢流动的雾/流体，随时间与状态变化 | **先做** |
| A | 更好的转场与微交互：惯性重排、弹性回弹 | 记录，暂缓 |
| C | 真 3D：磁贴有远近、分区切换是镜头移动、拖动有物理 | 记录，暂缓 |

B 和 D 一起做，因为它们本就是同一套东西——D 是背景着色器，B 是把 UI 合成进去再做后期，共用渲染循环和纹理管线。拆开要写两遍。

A 不需要动架构，CSS 与动画库即可；C 需要整个 UI 进 canvas，代价见下。

## 为什么不整个 UI 用 canvas 重画

评估过 PixiJS / Three.js 重写全部界面，否决。决定性的一条是**中文输入法**：canvas 里没有 DOM 输入框，IME 的候选窗定位、组合中文本、预编辑渲染全部要自己实现。这是 canvas UI 项目的经典坟场，而搜索框是 deskmind 的核心交互，它必须能打中文。

其次是命中测试、滚动、拖放、右键菜单全部要重写，以及无障碍完全丢失。

`drawElement` 恰好绕开了这一切：DOM 依然活着并响应事件，canvas 只是显示面。Chrome 的说明里明确保留了无障碍、页内查找、翻译、自动填充。

## 功耗是硬线

deskmind 常驻桌面，功耗特性与网页项目完全不同。CSS 动画由合成器处理且窗口不可见时自动暂停；自写的 `requestAnimationFrame` 循环没有这个待遇，而桌面层大部分时间被其他窗口完全盖住。

**验收标准（写效果之前定，做完舍不得砍）：**

- 空闲且可见时 GPU 占用不超过 **1–2%**
- **被遮挡时为 0%** —— 一帧都不画

后者不牺牲任何观感：没人在看的时候不画，用户永远感知不到。这是纯赚，不接受妥协。

## 分发：Evergreen 加硬性版本下限

`drawElement` 处于 origin trial 阶段，需要给 WebView2 传 `--enable-blink-features` 开启。WebView2 通过 `AdditionalBrowserArguments` 接受任意 Chromium 启动参数，Tauri 已暴露该入口。

**安装时检查 WebView2 版本，低于下限直接拒绝安装。** 这个产品面向愿意折腾的发烧友（ADR 0013），不需要服务所有用户。

### Considered Options

**Fixed Version 分发**（把运行时打进安装包）能彻底钉死版本，是"控制引擎"最彻底的形态。否决的原因是安装包从几 MB 涨到 150MB 以上，且 Chromium 的安全补丁不再自动到达用户、变成维护者的责任。

**纯特性检测降级**（不设版本门槛）最省事，但大部分用户看不到折射玻璃，而那正是这次要做的东西。

### Consequences

**S5 实测修正了这里的风险描述。** 在 Chromium 151（已过 148–150 的试用窗口）上，带 `--enable-blink-features=CanvasDrawElement` 时方法存在，不带时不存在。两个结论：

- **flag 不受 origin trial 期限约束**，比 trial 活得久。初稿担心的「试用期一到、所有用户同时失效」被高估了
- **方法名是 `drawElementImage`**，不是提案早期的 `drawElement`。特性检测必须同时接受两个名字

剩下的真实风险窄了一圈：**这个 flag 本身被 Chromium 移除**。它发生在特性正式发布并改名、或提案被放弃时——前者还是好消息。完整数据见 `spikes/s5-drawelement/FINDINGS.md`。

因此仍然**保留运行时特性检测**：`typeof ctx.drawElement === "function"` 不成立时，玻璃退回 `backdrop-filter`。这不是向下兼容——旧版本根本装不上——而是让未来的失效表现为"安静降级"而非"界面白屏"。

微软文档警告不要在生产版携带浏览器 flag，理由是引擎会变。我们知情并接受该风险，缓解手段就是上述特性检测。

## 玻璃折射的是界面，不是壁纸

第一版的玻璃由着色器自己合成壁纸和雾，然后折射那个合成结果。它便宜、不需要 flag，但**只能扭曲一张照片**——而玻璃压在照片上读起来是滤镜，压在内容上才读起来是玻璃。这是 iOS 的玻璃看着对、我们的看着不对的根本差别。

现在用 `drawElementImage` 把界面抓成纹理，玻璃采样它。为此 DOM 加了一层 `#world` 包住背景和界面，面板留在外面——**捕获的元素必须排除面板本身，否则会自我反馈**。

三条实现约束：

- **捕获限速到 30fps、半分辨率**。它是一次完整重绘，而结果只透过磨砂镜片看，陈旧一两帧看不出来
- **只在面板打开时捕获**。没有玻璃可画时捕获纯属浪费
- **背景层的 WebGL 上下文开了 `preserveDrawingBuffer`**。它在 `#world` 内部会被捕获，而已经交换走的绘制缓冲读回来是空的——那会让玻璃在一片黑上折射界面

降级路径完整保留：捕获不可用或抛错时 `hasUi` 归零，着色器自动退回程序化合成。这也是为什么那段代码没有删。

## 地基假设已验证

**WebGL 在挂到桌面层（`SetParent` 到 WorkerW/Progman 之下）的窗口里能拿到硬件加速上下文。** S4 spike 在桌面层窗口里读 `WEBGL_debug_renderer_info`，报的是真实 GPU 而非 SwiftShader，全屏着色器帧率正常。见 `spikes/s4-webgl/FINDINGS.md`。

一台机器上成立不等于所有机器上成立——驱动、远程桌面、虚拟机都可能把上下文打回软件渲染。所以 `src/background.ts` 的 `reportRenderer()` 在每次启动时读一次同一个值，掉进软件渲染就报 `console.error`，并留在 `window.__dmRenderer` 上。这条线一旦断了要立刻知道，而不是等到用户说「机器有点烫」。

同一个 spike 还发现浏览器不会替我们省电：被完全遮挡时 `requestAnimationFrame` 照样满帧。遮挡检测因此落在 `desktop::occluded()`。

## 功耗硬线已实测

3440x1440 单屏，`scripts/measure-gpu.ps1` 按 deskmind 整个进程树求 GPU 引擎占用，每秒一个样本：

| 场景 | GPU |
|---|---|
| 空闲可见，按显示器刷新率跑 | 23.5% |
| 空闲可见，30fps | 3.2% |
| 空闲可见，15fps（现状） | **1.83%** |
| 被最大化窗口完全遮挡 | **0.00%** |

两条线都过。让它过线的是三件事：

- **空闲时限到 15fps**。雾每秒漂 0.014 弧度，高亮光带 0.25——这个速度下 15 帧不是妥协，是比动画本身需要的还多。面板一开就回满帧。
- **没有玻璃时把玻璃层收成 1x1**。它那时只画透明，却仍按设备像素跑满一屏；一个被拉伸的透明像素和一屏透明长得一模一样。
- **不把自己算作遮挡自己的窗口**。`grab_focus` 之后前台一直是我们，而桌面窗口本来就有一屏那么大，矩形判定于是说「被盖满了」——盖住我们的是我们自己。这条修之前，用户搜索一次之后场景就冻在那里，而功耗读数是假的 0%。

前提仍然是硬件加速上下文：软件渲染只烧 CPU，3D 引擎上根本量不到这些数。
