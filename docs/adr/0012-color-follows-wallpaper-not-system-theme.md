# 配色跟随壁纸明暗，而不是系统深浅色主题

分区的文字色与半透明底色由**当前壁纸的明暗与主色**决定，不跟随 Windows 的深色/浅色模式。只有在读取不到壁纸时（纯色背景、多显示器异常）才退回跟随系统主题。

## 为什么这是刻意的

这条违反直觉，写下来是为了防止后来者把它「修正」成跟随系统主题。

分区是浮在壁纸之上的半透明卡片，决定其上文字能否读清的是**壁纸在那个位置的明暗**，与系统主题无关。用户完全可能在深色模式下使用一张亮色壁纸——此时若跟随系统，就会得到浅色文字配浅色壁纸，直接不可读。反之亦然。

## 亮度用来做什么，取决于表面

这条区分是实现启动台时才想清楚的，容易被后来者"修正"回去，所以写下来。

**启动台**（v1）在壁纸之上铺了一层自己的暗色纱幕，文字的可读性由纱幕保证，与壁纸明暗无关。所以在这个表面上，亮度驱动的是**纱幕浓度**——壁纸越亮，纱幕越浓——文字始终是浅色，不翻转。

**桌面分区**（v2）是半透明卡片直接浮在壁纸上，中间什么都没有，可读性完全取决于壁纸。那里才需要按亮度翻转文字色，也就是本 ADR 开头描述的规则。

换句话说：本 ADR 的「跟随壁纸」原则两处都成立，但落地成什么参数，取决于该表面有没有自己的底衬。

## 实现

读取壁纸图像，同时得出两个值：平均亮度（决定文字用深色还是浅色）与主色（决定分区半透明底色的色相）。这与 ADR 0011 中的壁纸取色是同一段代码，读壁纸只做一次。

v1 只计算一次全局亮度。更正确的做法是按每个分区所在的屏幕区域分别取样——处理壁纸左半亮、右半暗的情况——但推迟到 v2。

主色不取平均色：平均色对任何非单色图片都是一坨泥。做法是量化到每通道 4 位，丢弃接近灰的、过暗的、过亮的像素，取剩下最多的那一桶。

壁纸**不重新编码**，前端通过 asset protocol 直接引用原文件。早期版本压到 1280 宽转成 base64 内嵌，在高分屏上明显发虚，而且换壁纸时要重新编码几 MB 再走 IPC。

## Consequences

用户切换壁纸时必须重新计算并刷新分区配色，因此需要监听壁纸变更。

如果未来提供「手动指定配色」的选项，它应当作为覆盖项存在，而不是取代这套自动逻辑。
